# Loop runbook — Build the offline Android K-line strategy screening app (Expo + React Native + TypeScript): read the PC-generated SQLite K-line db, run 25 pure-OHLCV strategies post-market, score 1-5 stars via 3-layer filtering, and emit a rich searchable BUY/SELL recommendation report

> A runnable closed-loop design generated by loop-constructor. Follow it as a loop: make a small change → run the stage check → read the result → fix → repeat until the check passes, then advance.
> **Altitude:** medium — Single-agent, strictly sequential gated stages (each consumes the prior stage's stable artifact: db layer -> indicators -> signals -> report -> scheduling -> e2e). No independent fan-out work exists; reversible (all new local code, git-tracked, dual remote). Human reviews at each gate.

## Tech Stack
- **Framework:** Expo + React Native
- **Language:** TypeScript
- **Database:** expo-sqlite
- **UI:** React Native with Native Base / StyleSheet
- **Testing:** Jest + React Native Testing Library
- **Packaging:** Expo EAS Build (Android APK)
- **Charts:** react-native-svg

## Hard constraints
- Minimal viable change; don't touch unrelated files.
- Don't change public APIs / add deps without justification.
- No production resources.
- On a requirement contradiction → STOP and report.

## Why this shape (decision log)
> The D0–D6 selection procedure that derived this loop's shape.
- **D0** (loop) — runnable checks exist per stage (npm run build, Jest unit tests against a python oracle, bigdemo e2e script exit code, export verifier) — done is machine-decidable without a human reading output
- **D1** (staged (5 seams, 6 stages)) — stable checkable artifacts handed across each seam: schema-read db layer -> indicator outputs -> signal+star pool -> rendered report+export -> scheduled run+import -> e2e report; each seam gates the next
- **D2** (plan_execute_verify x5 + review (qa)) — scaffold/indicators/strategy/report/schedule are risky structured builds needing mid-flight correction (plan_execute_verify); qa_integration is a correctness judgment on the whole artifact (review). checks assert OUTCOME against an independent python oracle, not a proxy
- **D3** (in_the_loop) — user SOP requires confirming before file changes AND the financial-correctness check can pass-while-wrong (a wrong indicator value still builds green) — weakest check wins => human in at every gate
- **D4** (medium) — stages are strictly sequential (each depends on the prior); no two stages are independent fan-out work
- **D5** (caps + escalate, one loopback) — per-stage caps 3-4; on_failure escalates to human except qa_integration which loops back to strategy_engine when e2e reveals an engine contract bug (valid upstream ancestor). outer budget 4
- **D6** (completeness_first) — iteration boundaries are expensive (npm build + context rebuild, slow) and checks are slow (bigdemo e2e ~minutes) => few long thorough passes: low caps, large per-stage scope, thorough full-suite+oracle checks, review at the few gates. re-tuned D2->plan_execute_verify, D3->in_the_loop, D5->low caps

## Stages (run in dependency order; each stage is its own gated loop)
> After a stage gate goes green, commit/checkpoint it; on a loopback, reset to the last green checkpoint rather than editing forward.

### Stage 1 — `scaffold` · pattern: plan_execute_verify

- **Done when:** Expo + React Native + TypeScript project initialized; expo-sqlite reader opens the demo db and returns table list + kline_daily row count matching meta; git repo initialized with Gitee + GitHub remotes and an initial commit pushed
- **Check (run — the gate):** `npm run build && python3 scripts/verify_schema.py --db kline_1y_smalldemo.sqlite` · expect: `pass`
- **Falsifiable when:** the SQLite DB reader cannot open the demo db or returns 0 rows for kline_daily while meta reports 288 stocks — verify_schema.py exits non-zero
- **Passing-but-wrong (ruled out):** npm run build is green but the DB import path is stubbed (returns a hardcoded list) — ruled out: verify_schema.py opens the real db and asserts table presence + row-count parity with meta, failing on a stub
- **Depends on:** — (entry stage) · admit downstream only once this check passes.
- **Stop:** max 3 iterations; failure branches:
    - npm / Expo environment cannot produce a green build (toolchain broken, not our code)
- **On failure:** escalate.

### Stage 2 — `indicators` · pattern: plan_execute_verify

- **Done when:** MA/EMA/RSI/MACD/BOLL/ATR/CCI/MOM/ROC implemented in TypeScript; values match scripts/indicator_oracle.py within 1e-6 on fixed fixtures; bigdemo precompute completes in bounded time using async/await + pagination (no main-thread block)
- **Check (run — the gate):** `npm test -- --testPathPattern='IndicatorTest'` · expect: `pass`
- **Falsifiable when:** an indicator returns a wrong value for a hand-computed vector (e.g. RSI(14) on a known 15-bar series, or EMA smoothing) — the test asserts exact values and goes red
- **Passing-but-wrong (ruled out):** the test only asserts the function returns a non-null number[] of length==N (shape check) — ruled out: IndicatorTest asserts exact values against scripts/indicator_oracle.py output within 1e-6 tolerance for RSI/MACD/BOLL/ATR on fixed fixtures
- **Depends on:** `scaffold` · admit downstream only once this check passes.
- **Stop:** max 4 iterations; failure branches:
    - 3 consecutive same-type failures
    - indicator math diverges from oracle beyond 1e-6 on more than one fixture
- **On failure:** escalate.

#### Stage 2 性能保障要求（防 300s 超时）

> 目标：在指标计算阶段提前埋点，确保大数据量（bigdemo 202万行 / ~288只股票×25策略）下不超 300s 预算。

**1. 强制埋点（performance.now()）**
- Hermes 引擎原生支持 `performance.now()`（亚毫秒级精度），全量用于包裹"单只股票完整指标计算"与"单指标计算"两个粒度。
- 输出 P50 / P95 / Max 耗时日志，定位瓶颈指标（经验上 MACD/BOLL/GuppyMA 是热点）。
- 埋点代码与指标代码同文件，通过 `__DEV__` 开关控制日志输出，生产构建自动关闭。

**2. 分阶段多线程策略**

| 阶段 | 环境 | 方案 | 说明 |
|---|---|---|---|
| 迭代期 | Expo Go | 单线程 + 分片让出 | Expo Go 不支持任何原生多线程包 |
| 生产期 | EAS Build | react-native-multithreading（JSI 真线程） | 需 custom dev client，线程池 2-4 线程按股票分片并行 |

**3. Expo Go 迭代期具体措施（必须实现）**
- 启动入口用 `InteractionManager.runAfterInteractions` 延后，避免阻塞列表滑动/切换动画。
- 核心循环采用**分页批处理**：每批 5-10 只股票，批与批之间用 `setImmediate` 让出主线程（Hermes 下无 4ms 钳制，优于 setTimeout(0)）。
- 进度条每 N 批更新一次，可选 `requestAnimationFrame` 平滑动画。
- **缓存中间结果**：EMA/MACD/BOLL 序列在单只股票内只算一次，策略引擎复用，禁止重复计算。
- **三级过滤降负载**：粗筛（趋势方向）→ 中筛（形态确认）→ 精筛（背离/极值），减少进入重计算的股票数。
- 禁止使用：Web Worker（RN 不支持）、expo-worker（已废弃）、react-native-multithreading（Expo Go 不支持）。

**4. EAS Build 生产期升级路径**
- 切换为 development build / EAS Build，获得原生模块能力。
- 首选接入 `react-native-multithreading`，开线程池（2-4 线程）按股票代码分片并行计算指标；主线程仅负责 UI 与汇总。
- 进阶方案：把 RSI/MACD/KDJ 等计算密集型指标用 Kotlin 写成原生模块，通过 JSI 暴露。
- 保留迭代期的分片 + 缓存逻辑作为降级路径，多线程失败时仍可用。
- CPU 级分析用 Hermes sampling profiler。

**5. 性能验收门**
- 单只股票全指标计算 P95 ≤ 800ms（bigdemo 单只约 1200 根 K 线）。
- 全量 288 只股票串行计算 ≤ 240s（留 60s 余量给策略引擎+报告生成）。
- 若 Expo Go 下 P95 > 1500ms 或全量 > 280s，**立即触发 EAS Build 升级路径**，不等 qa_integration 阶段才发现超时。

### Stage 3 — `strategy_engine` · pattern: plan_execute_verify

- **Done when:** All 25 strategies implemented; signal pool (stock/strategy/direction/triggerDay/triggerPrice) produced; 3-layer filter assigns 1-5 stars per star_thresholds; stop_loss = max(triggerDayLow, MA20); outputs match scripts/strategy_oracle.py on a 12-stock sample covering all 8 groups
- **Check (run — the gate):** `npm test -- --testPathPattern='StrategyTest'` · expect: `pass`
- **Falsifiable when:** a strategy misfires (e.g. T01 golden-cross reported on a death-cross day) or star rating violates star_thresholds — StrategyTest asserts direction+triggered per sampled stock against the oracle and goes red
- **Passing-but-wrong (ruled out):** the test only asserts the signal pool is non-empty (count>0) — ruled out: StrategyTest asserts per-strategy direction and triggered-day parity with scripts/strategy_oracle.py on a 12-stock sample covering all 8 groups, plus stop_loss == max(triggerLow, MA20)
- **Depends on:** `indicators` · admit downstream only once this check passes.
- **Stop:** max 4 iterations; failure branches:
    - 3 consecutive same-type failures
    - oracle vs app disagree on >2 sampled stocks and cannot be reconciled from the Manifest
- **On failure:** escalate.

### Stage 4 — `report_ui` · pattern: plan_execute_verify

- **Done when:** Three views (overview/detail/strategy) render in React Native; K-line chart overlays MA+BOLL with signal markers using react-native-svg; 6 search filters combinable; CSV+text export produces a file; mobile UX per constraints (scroll/tabs/navigation). ViewModel signal-list parity with engine verified
- **Check (run — the gate):** `npm test -- --testPathPattern='ReportViewModelTest' && python3 scripts/verify_export.py --out /tmp/app_export.csv` · expect: `pass`
- **Falsifiable when:** the ViewModel emits a report that drops a BUY signal present in the engine output, or export CSV is missing columns/rows — the test/verify go non-zero
- **Passing-but-wrong (ruled out):** the test only asserts the ViewModel is not null / export file exists — ruled out: ReportViewModelTest asserts signal-list parity with the engine and verify_export.py asserts header+row counts match the in-memory report
- **Depends on:** `strategy_engine` · admit downstream only once this check passes.
- **Stop:** max 4 iterations; failure branches:
    - 3 consecutive same-type failures
    - a UI change modified a data-layer file (module-boundary violation)
- **On failure:** escalate.

### Stage 5 — `schedule_import` · pattern: plan_execute_verify

- **Done when:** expo-background-fetch enqueues a unique post-market run at 16:00 (±10min); manual single-strategy trigger works; DB import button shows confirm dialog and auto-backs-up the previous db before overwrite; missed-run auto-catchup on app open. All verified by unit tests
- **Check (run — the gate):** `npm test -- --testPathPattern='ScheduleImportTest'` · expect: `pass`
- **Falsifiable when:** Background fetch at 16:00 is not registered, or importing a new db overwrites the old one without backup / without confirm — the test asserts backup file exists and confirm gate is invoked
- **Passing-but-wrong (ruled out):** the test only asserts the import function returns true — ruled out: ScheduleImportTest asserts (a) a backup of the previous db is created before overwrite, (b) the confirm dialog state is required, (c) background fetch work is scheduled with the 16:00 constraint
- **Depends on:** `strategy_engine`, `report_ui` · admit downstream only once this check passes.
- **Stop:** max 4 iterations; failure branches:
    - 3 consecutive same-type failures
    - Background fetch scheduling cannot be made testable on the target API level
- **On failure:** escalate.

### Stage 6 — `qa_integration` · pattern: review

- **Done when:** Full pipeline runs on bigdemo (2.02M rows) within 300s, emits non-empty report JSON with all 25 strategies represented; all prior unit tests green; no data-layer regression; QA checklist passed; version tagged and pushed to Gitee+GitHub
- **Check (run — the gate):** `npm run build && npm test && python3 scripts/verify_e2e_bigdemo.py --db kline_5y_bigdemo.sqlite --timeout 300` · expect: `pass`
- **Falsifiable when:** the full pipeline on bigdemo throws, exceeds the 300s budget, or emits an empty report — verify_e2e_bigdemo.py exits non-zero; or any prior unit test regresses
- **Passing-but-wrong (ruled out):** npm run build green but verify_e2e only checks the build exists — ruled out: verify_e2e_bigdemo.py drives the engine module on the 202万-row db, asserts completion within --timeout and a non-empty report JSON with all 25 strategies represented
- **Depends on:** `schedule_import` · admit downstream only once this check passes.
- **Stop:** max 3 iterations; failure branches:
    - e2e exceeds 300s budget after 3 tuning passes
    - a prior unit test regresses after the integration change
- **On failure:** loop back to `strategy_engine`.

## Stop conditions (overall)
- **Success:** all 6 stages pass in dependency order; app builds; bigdemo e2e completes within 300s and emits a non-empty report with all 25 strategies; all unit tests green; version tagged and pushed to both remotes
- **Max iterations (budget cap):** 4
- **Failure branches:**
  - any stage exhausts its max_iterations without passing its check
  - a downstream stage forces a redesign of an accepted upstream stage twice
  - a data-layer file is modified by a UI-stage change (module-boundary violation)
- **Escalate to a human when:**
  - performance on bigdemo exceeds budget and requires an architecture change to the scaffold stage
  - oracle vs app disagree beyond tolerance and cannot be resolved without an external market-data source

## Terminal states
- **SUCCESS** — all 6 stages pass in dependency order; app builds; bigdemo e2e completes within 300s and emits a non-empty report with all 25 strategies; all unit tests green; version tagged and pushed to both remotes → done.
- **STOPPED_UNMET** — a max-iteration cap is hit or a failure branch fires: stop, report the last green stage and the unmet gate, hand back the partial diff, do NOT merge. Never relax a gate to force a pass.
- **ESCALATE** — one of the escalate triggers above fires: hand to a human.

## Human placement
- in_the_loop

## Checker (separate, fresh-context)
- fresh-context reviewer sees only the diff + the per-stage acceptance checks + LOOP_MANIFEST.yaml; flags (a) indicator/strategy numeric correctness vs the python oracle, (b) any backward-compat regression in existing modules, (c) any UI-stage change that touches a data-layer file (module-boundary violation per Manifest constraint), (d) missing confirm-gate before file changes

## Risk guards
- **reward hacking / test overfitting (agent weakens the oracle or test to pass)** → the python oracle is independent of the TypeScript tests; the maker/checker diffs test+oracle files and rejects weakening; numeric tolerance is fixed at 1e-6
- **backward-compat violation (UI change breaks data layer / old function removed)** → Manifest constraint forbids data-layer edits from UI stages; enforced in maker_checker scope + git path guard; regression gate in qa_integration
- **context drift across the long sequential build** → .loop/run-state.md ledger + selection_log pins per-stage scope; each stage re-reads LOOP_MANIFEST.yaml before coding
- **error amplification (a wrong upstream artifact poisons later gates)** → stage gates run in dependency order; a downstream failure that implicates an upstream gate loops back (qa->strategy_engine) rather than head-banging in place
- **token blowup on a large from-scratch app** → completeness-first profile => low caps (outer 4, per-stage 3-4), bounded per-stage scope, no full-file rewrites; each stage is a focused commit
- **permission blast radius (app reaches network / external resources)** → Manifest mandates pure offline, no network permission; imports are user-initiated file picks only; no external calls in any stage

## Harness primitives
- git worktree isolation for reversible per-stage work
- dual-remote git sync (Gitee primary, GitHub mirror) — push after each stage commit
- .loop/run-state.md scratch ledger holding which stage is done + next action across context resets
- pre-commit hook runs the current stage's check as a deterministic gate
- python3 oracle/verify scripts (scripts/indicator_oracle.py, strategy_oracle.py, verify_schema.py, verify_export.py, verify_e2e_bigdemo.py) are stage deliverables and the independent source of truth for numeric correctness
